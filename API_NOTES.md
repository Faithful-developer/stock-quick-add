# API notes — смена способа оплаты

Что здесь: как установлены маршруты для инструмента «Оплата», что ещё не
подтверждено, и какие curl прогнать, чтобы закрыть остаток. Приём остатков
описан в шапке `panel.js` — он проверен на живом тенанте, здесь его нет.

Всё ниже установлено **без авторизации** методом сравнения ответов на
`demo.ox-sys.com` (2026-09-03). У бэкенда (Symfony за nginx) три
различимых ответа:

| Ответ | Смысл |
| --- | --- |
| `302 → /login` | маршрут есть, закрыт HTML-файрволом |
| `404 {"code":404,"message":"Not Found"}` | маршрут совпал, сущности нет |
| `405 … No route found for "<METHOD> <path>"` + `Allow:` | для этого метода маршрута нет |

Контроль: **любой неизвестный путь из одного сегмента отвечает
`405 Allow: DELETE`.** Это базовая линия, с которой сравнивается всё остальное.

```
GET  /zzz-random-9182     -> 405  Allow: DELETE                 <- базовая линия
POST /sells/30            -> 405  Allow: GET, PUT, PATCH, DELETE
GET  /sells/30            -> 404  {"code":404,"message":"Not Found"}
GET  /sells/abc           -> 405  Allow: PUT, PATCH, DELETE      (нечисловой id — другой маршрут)
POST /sells/30/patch      -> 405  Allow: PATCH
POST /sells-list          -> 405  Allow: DELETE, GET
POST /payment-methods     -> 405  Allow: DELETE, GET
POST /payments-methods    -> 405  Allow: DELETE                 <- базовая линия: не существует
POST /paymentMethods      -> 405  Allow: DELETE                 <- не существует
POST /zones               -> 302 → /login                       (маршрут есть)
GET  /api/sells-list      -> 404                                (префикса /api нет)
```

## Что подтверждено

**`GET /sells/{id}` существует.** `POST /sells/30` отвергается с
`Allow: GET, PUT, PATCH, DELETE`, значит GET для числового id зарегистрирован.
`404` на demo — уровень сущности (там просто нет продажи 30), не маршрута.
Поэтому прямой поиск по номеру — основной путь; поле даты в панели появляется
только если сервер ответил `405`.

**`PATCH /sells/{id}/patch` существует** и принимает ровно один метод.

**`GET /payment-methods` существует** — `Allow: DELETE, GET`, на один метод
богаче базовой линии, та же сигнатура, что у заведомо рабочего `/sells-list`.
Варианты `/payments-methods` и `/paymentMethods` — на базовой линии, их нет.
Ручной справочник id→название не нужен.

**`zone[0]=1` — не константа.** `/zones` — отдельный маршрут, зоны у каждого
тенанта свои. Панель фильтр по зоне не хардкодит: сначала запрос без него,
потом зона найденной продажи, `1` — последним.

## Что открыто — форма ответа `GET /sells/{id}`

Единственное, чего не даёт неавторизованный запрос, и единственное, от чего
зависит тело PATCH. Панель не гадает: для каждого из `customer`, `sellRecords`,
`note`, `payments`, `status` перебирает список путей-кандидатов (`PM_FIELDS`
в `payment.js`), берёт первый найденный и **не отправляет запись**, если
обязательного поля нет — оператор видит «В ответе нет полей для записи: …».

Два переключателя в `payment.js` (`PM_BODY`). **2026-09-04: режим `echo` на
живом тенанте дал HTTP 422** — Symfony-форма отвергает лишние поля. Поэтому
теперь по умолчанию тело собирается ровно по образцу curl:

* `sellRecordsMode: 'minimal'` — `[{"assistants":[…],"managers":[…]}]`, где
  элементы приводятся к id (`pmIdOf`). `'echo'` отправлял бы вложенные
  `product`/`variation` целиком — это и есть источник 422.
* `paymentKeysMode: 'curl'` — только `paymentMethod, price, type`. `'echo'`
  добавлял `id`, `createdAt` и т.п. → «This form should not contain extra fields».

**Второй источник 422 (2026-09-04, `urolbek`): `price` в GET — мультивалютный
объект** `{"first":"UZS","ratio":{…},"order":["UZS","USD"],"UZS":16373000,"USD":1364.42}`.
Так же устроен `totalPrice`. PATCH ждёт число в основной валюте
(`"price":16373000`), и `pmAmountOf` берёт значение по ключу `first`
(запасные — `order[0]`, `UZS`). Сумма на карточке и в журнале — тоже она.

Если 422 повторится, его причина теперь видна: `serverMessage` в `panel.js`
разбирает `violations[]` и дерево `errors.children` и показывает
«поле: сообщение», а тело запроса и ответ сервера пишутся в консоль панели
(`[payment] PATCH отклонён`).

## Curl, чтобы закрыть открытое

Токен — только в заголовке, не в URL и не в файл.

```bash
HOST=<субдомен>.ox-sys.com
read -rs TOKEN
SELL=30

# a. одна продажа — форма ответа
curl -s -H "auth-token: $TOKEN" -H "authorization: Bearer $TOKEN" \
     -H 'accept: application/json' "https://$HOST/sells/$SELL" | python3 -m json.tool

# b. способы оплаты — форма списка и поле с названием
curl -s -H "auth-token: $TOKEN" -H "authorization: Bearer $TOKEN" \
     -H 'accept: application/json' "https://$HOST/payment-methods" | python3 -m json.tool

# c. список без фильтра зоны — если отдаёт записи, zone[0] необязателен
curl -s -G -H "auth-token: $TOKEN" -H 'accept: application/json' \
  --data-urlencode 'size=5' --data-urlencode 'page=1' \
  --data-urlencode 'finishedTime[min]=2024-10-03 00:00:00' \
  --data-urlencode 'finishedTime[max]=2024-10-03 23:59:59' \
  --data-urlencode 'position=finished' \
  "https://$HOST/sells-list" | python3 -m json.tool | head -40
```

Самая ценная проверка — не curl: сменить оплату через обычный интерфейс
ox-sys с открытым devtools → Network и сравнить тело того PATCH с тем, что
панель показывает после успешной записи. Это ловит всё, что не ловят моки.

## Эталон: PATCH самого интерфейса ox-sys (2026-09-04, `urolbek`)

Снято из devtools при смене оплаты у продажи с двумя оплатами:

```json
{"sellRecords":[{"assistants":[],"managers":[]},{"assistants":[],"managers":[]}],
 "note":null,
 "payments":[{"paymentMethod":1,"price":12244000,"type":"sell"},
             {"paymentMethod":7,"price":16000000,"type":"sell"}],
 "status":"completed"}
```

Что из этого следует и что делает панель:

* `customer` в теле **нет** — панель его тоже не шлёт.
* `sellRecords` — по одной заглушке на каждую запись продажи (панель берёт
  их число из GET, `assistants`/`managers` — id из GET, если есть).
* `payments` — **все** строки, каждая только `paymentMethod, price, type`;
  строк может быть сколько угодно. В панели у каждой строки свой селект
  нового способа (плюс «Все оплаты сразу»); меняются любые строки за одно
  подтверждение, нетронутые уходят эхом с суммами байт в байт. В журнал —
  по записи на каждую изменённую строку.

## Что панель гарантирует

* Тело PATCH собирается только из свежего GET, сделанного **прямо перед
  записью**, и сверяется со слепком того, что видел оператор. Изменилась
  продажа между показом и подтверждением — ничего не пишется.
* `price` уходит байт в байт: числа читаются как исходный текст
  (`JSON.rawJSON`, Chrome 114+). Без него — проверка, что каждое число
  встречается в ответе целым токеном; иначе отказ.
* Раздельная оплата: любые строки меняются за один PATCH и одно подтверждение.
  Слепок (fingerprint) покрывает все строки — изменилась любая, запись отменяется.
* 401/403 → «Сессия истекла или нет прав». Остальное → сообщение сервера,
  если есть, иначе код.
* Журнал: 500 последних изменений в `chrome.storage.local` (`paymentLog`),
  CSV с BOM на странице настроек.
